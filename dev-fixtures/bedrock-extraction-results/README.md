# Bedrock extraction results

## Automatic local archives

Docker Compose also saves each successful rule extraction in this directory as
`<document-id>_YYYY-MM-DD_HH-MM-SS-microsecondsZ.rules.json`. The timestamp is UTC.
These additional files remain unreviewed drafts, like the reference results below.
Workflow outputs retain candidates even when validation fails. Inspect the paired
report in `../Reports_for_results/` for per-record findings and all feedback rounds.
Existing files are never overwritten. The job's original `rules.json` remains in
backend storage and continues to serve the API. CLI runs can opt into the same
behavior by setting `ODOS_RULE_EXTRACTION_ARCHIVE_DIR` to a writable directory.

## Reference results

**REAL LLM OUTPUT – unreviewed drafts.** Unlike [../rule-json-examples/](../rule-json-examples/README.md) (hand-modeled, simulated), the files here were generated by `odos extract-rules` with Amazon Bedrock (see [bedrock-rule-extraction.md](../../Documentation/bedrock-rule-extraction.md)). Every record has `review.status: "draft"`; none is a legal compliance decision. Each file's `_generation` block records model, region, scope, token counts and rejected records.

| File | Document | Scope | Generated with |
|---|---|---|---|
| `mbo-paragraph-6.rules.json` | Musterbauordnung (MBO), `document.json` of a local processing job | `doc/teil-2/par-6` (§ 6 Abstandsflächen, Abstände), 21 rules | `ODOS_BEDROCK_MAX_TOKENS=32000 odos extract-rules <document.json> --element-id doc/teil-2/par-6 -o dev-fixtures/bedrock-extraction-results/mbo-paragraph-6.rules.json` |
| `mbo-paragraph-6.v2.rules.json` | MBO, as above | `doc/teil-2/par-6`, prompt version 2, 20 rules (1 rejected) | as above, `-o .../mbo-paragraph-6.v2.rules.json` |
| `eu-2023-1230-article-10.v2.rules.json` | Verordnung (EU) 2023/1230, `document.json` of a local processing job | `doc/chp-2/art-10` (Artikel 10 Pflichten der Hersteller), prompt version 2, 25 rules | `ODOS_BEDROCK_MAX_TOKENS=64000 odos extract-rules <document.json> --element-id doc/chp-2/art-10 -o .../eu-2023-1230-article-10.v2.rules.json` |
| `eu-2023-1230-article-10.v3.rules.json` | Verordnung (EU) 2023/1230, as above | `doc/chp-2/art-10`, prompt version 3, 25 rules (0 rejected, 2 flagged); rule IDs are not yet document-scoped | as the `.v2` file, `-o .../eu-2023-1230-article-10.v3.rules.json` |

The source `document.json` is not part of the repository (`backend/storage/` is git-ignored); element IDs, pages and sentence IDs refer to the current parser output.

`mbo-paragraph-6.rules.json` was generated with prompt version 1 (before `odos.llm.profiles` and `odos.llm.rule_checks`) and is kept unchanged as the baseline: `backend/tests/test_rule_quality.py` pins its hash and checks that the current validation detects its known problems (German fact identifiers, a determined value split into two minimums, alternatives emitted both as exceptions and as separate rules).

The two `.v2` files were generated with prompt version 2 and are kept unchanged as well (pinned in `backend/tests/test_rule_engine_v3.py`). Prompt version 3 and its checks were developed from their evaluation: the checks must detect the problems found there (German fact identifiers, a roof-pitch threshold only in descriptions, an alternative that turns `==` into `>=`, building classes as strings, a retention period as a number instead of a temporal requirement, inconsistent actor names). These files predate `_generation.coverage`, `schemaRepairs` and `rulesRejected[].candidate`.

The MBO § 6 run with prompt version 3 failed because the model's answer was not valid JSON; there is no `mbo-paragraph-6.v3.rules.json`. At that time the answer was neither retried nor kept. Both are done now (one correction request, private diagnostic file), see `Documentation/bedrock-rule-extraction.md`.
